# Mini-SIEM — Detection Engineering Platform

A working SIEM: multi-source log ingestion, ECS normalization, enrichment,
Sigma-compatible detection, stateful correlation, behavioral baselining, entity risk
scoring, automatic case management and response playbooks — plus **a search query
language** and **real-time streaming detection**, with measured detection quality
enforced in CI.

**Runtime dependencies: Python 3.10+ and PyYAML.** Nothing else is required to run
the full pipeline. OpenSearch and Dashboards are optional extras.

```bash
pip install -r requirements.txt
python tools/generate_logs.py
python -m siem.cli analyze --input-dir sample_logs --html out/dashboard.html
open out/dashboard.html

python -m siem.cli shell --input-dir sample_logs            # interactive search
python -m siem.cli stream --input-dir sample_logs --replay  # live detection
```

## Measured detection quality

Scored against a labelled corpus of 1,136 events containing 14 attack behaviours
across 5 scenarios, mixed with benign traffic deliberately designed to produce
false positives.

| Metric | Result |
|---|---|
| **Precision** | **100%** — 28 alerts raised, 28 attributable to real attacks |
| **Recall** | **100%** — 14 of 14 labelled attack behaviours detected |
| **F1** | **1.000** |
| Events analysed | 1,136 across 5 log sources |
| Cases opened | 8 |
| ATT&CK techniques detected | 10 (T1059, T1059.001, T1070.001, T1078, T1098, T1110.001, T1110.003, T1190, T1548, T1595.003) |
| Rules | 15 atomic (Sigma YAML) + 3 correlation + 3 behavioral |
| Tests | 64, all passing |

Reproduce: `python -m siem.cli metrics --input-dir sample_logs --threshold-sweep`

These numbers are generated by the committed harness, not typed by hand, and CI
fails the build if precision or recall drops below 80%.

> **Honest framing:** 100% on a synthetic corpus proves the pipeline is internally
> consistent, not that it would score the same against live adversary traffic.
> The corpus is adversarially designed — it includes a misconfigured backup agent
> that burst-retries, a crawler generating 404s, and users mistyping passwords —
> but it is still a corpus I wrote. See [docs/TUNING.md](docs/TUNING.md) for the
> false positives this produced before tuning, and [docs/HONEYPOT.md](docs/HONEYPOT.md)
> for running it against real attacker traffic.

## Architecture

```
  SOURCES              PIPELINE                           OUTPUTS
┌──────────────┐     ┌──────────────────────────┐      ┌────────────────┐
│ Linux auth   │────▶│ 1. Parse    → ECS        │      │ Console report │
│ sudo         │     │ 2. Enrich   → geo/intel/ │      │ HTML dashboard │
│ Nginx access │────▶│              asset/ident │─────▶│ ECS NDJSON     │
│ Windows Sec  │     │ 3. Detect   → Sigma YAML │      │ OpenSearch bulk│
│ Suricata EVE │────▶│ 4. Correlate→ sequences  │      │ Case files     │
│ Cowrie honey │     │ 5. Score    → risk+decay │      │ metrics.json   │
└──────────────┘     │ 6. Respond  → playbooks  │      └────────────────┘
                     └──────────────────────────┘
```

**Why ECS normalization matters.** A Windows 4625 and a Linux "Failed password"
become the same event shape, so one brute-force rule covers both platforms rather
than one rule per log format. This is the decision that separates a SIEM from a
collection of per-logtype scripts.

**Three detection tiers:**

| Tier | Catches | Implementation |
|---|---|---|
| Atomic | Known-bad patterns in single events | Sigma YAML, `rules/atomic/` |
| Stateful | Logic needing memory of prior events | `siem/correlation.py` |
| Behavioral | Deviation from a learned baseline | `siem/correlation.py::Baseline` |
| Correlation | Multi-stage chains across sources | Sequence YAML, `rules/correlation/` |

**Risk scoring instead of alert-per-rule.** Twelve medium alerts about one IP is
twelve tickets with the signal spread across all of them. Here, alerts accumulate
onto *entities* (IP, user, host) with contextual multipliers — crown-jewel asset
2.0×, threat-intel match 1.6×, privileged account 1.5× — and a 24-hour half-life
decay so stale risk fades. One case opens per entity, containing the whole story.

## Interactive search (SIEMQL)

Detection rules answer *"did this known-bad thing happen?"*. Search answers
*"what the hell happened?"* — the question an analyst actually asks.

```bash
python -m siem.cli shell --input-dir sample_logs
python -m siem.cli search 'event.outcome = failure | top source.ip 10'
python -m siem.cli search --examples
```

Pipeline syntax in the style of SPL or KQL:

```
event.outcome = failure
  | stats count, dc(user.name) as users by source.ip
  | sort -count
```

```
  SOURCE.IP      COUNT  USERS
  ─────────────  ─────  ─────
  10.0.0.41      84     1       ← misconfigured backup agent, one account
  203.0.113.45   60     3       ← brute force, few accounts
  198.51.100.77  42     14      ← password spray, many accounts
```

Three different stories in one table, and no rule told you — you asked. Supports
`=` `!=` `>` `>=` `<` `<=` `=~` `contains` `startswith` `endswith` `in [..]`
`and/or/not`, and the commands `where`, `stats`, `sort`, `head`, `tail`, `fields`,
`top`, `rare`, `timechart`, `eval`. Full reference: [docs/QUERY.md](docs/QUERY.md).

## Real-time streaming

Batch analysis tells you what happened yesterday. Streaming tells you it is
happening now.

```bash
# Follow live logs
python -m siem.cli stream --auth /var/log/auth.log --nginx /var/log/nginx/access.log

# Replay the sample corpus through the streaming engine (best demo)
python -m siem.cli stream --input-dir sample_logs --replay --speed 60
```

Alerts fire mid-stream, the moment there is enough evidence:

```
22:00:12 HIGH      SSH Brute Force ← 203.0.113.45  [T1110.001]
 ▶ CASE OPENED CASE-20260921-59A5A6  CRITICAL | SLA 1h | risk 207
    → Block source IP at the perimeter firewall
22:00:40 CRITICAL  Successful Authentication After Repeated Failures ← 203.0.113.45
```

Engineering details that make it real rather than a loop over a file:

- **Bounded memory** — sliding window trimmed to the longest rule window; a test asserts memory stays flat over 400 events
- **Incremental evaluation** — only rules matching the arriving event are re-run, and only against events sharing its group key
- **Exactly-once alerting** — fingerprints prevent re-emitting findings as windows overlap
- **Log rotation and truncation handled** — inode change and size shrink both detected
- **Checkpointed offsets** — restart resumes instead of replaying and re-alerting
- **Partial-line buffering** — a line still being written is held until its newline arrives

Full reference: [docs/STREAMING.md](docs/STREAMING.md).

## What it detects

**Linux / SSH** — brute force (sliding window), password spray (distinct-username
counting), successful auth after repeated failures, privilege escalation after
external login.

**Web** — directory scanning, sensitive file probing (`.env`, `.git`, `.aws`), SQL
injection, XSS, path traversal, attack-tool user agents.

**Windows** — 4625 brute force, privileged group modification, audit log cleared,
encoded PowerShell and LOLBin execution.

**Network / Deception** — Suricata IDS alerts, honeypot interaction and
post-compromise command execution.

**Correlation chains** — recon → credential attack → compromise; web exploitation →
host access. A complete chain scores 95 and opens a critical case with a 1-hour SLA.

## Writing a detection

Rules are data, not code — reviewable in a pull request and convertible to Splunk
SPL or Elastic KQL with `sigma-cli`.

```yaml
title: SSH Brute Force
id: ssh_brute_force
level: high
tags: [attack.t1110.001, attack.credential_access]
entity: source.ip
detection:
  selection:
    event.category: authentication
    event.outcome: failure
    event.provider: [sshd, cowrie]
  threshold:
    group_by: [source.ip]
    count: 10
    window: 60s
  condition: selection
falsepositives:
  - Misconfigured automation with stale credentials
response:
  - Confirm whether any authentication from this source later succeeded
  - Block the source at the perimeter if external and unrecognised
```

CI rejects any rule missing `falsepositives` or `response`. Supported Sigma
features: `selection`/`filter` blocks, `and`/`or`/`not` conditions, `1 of`/`all of`,
and the `contains`, `startswith`, `endswith`, `re`, `gt`, `gte`, `lt`, `lte`
modifiers.

## Design decisions worth defending

**Response playbooks are Python, not a workflow GUI.** They get unit tests, code
review and version control like everything else.

**Automated blocking is held behind a human decision** except for honeypot contact,
where false positives are impossible by construction. An attacker who knows you
auto-block can spoof traffic from your payment processor's range and take your
business offline for you.

**One rule is deliberately disabled.** `003_account_compromise.yml` cannot be
expressed statelessly — matching `event.outcome: success` fires on every legitimate
login. Enabled, it produced 56 critical alerts on a corpus containing 2 real
compromises, a 96% false positive rate. The file is kept for its ATT&CK mapping and
response guidance; the real implementation is stateful. A regression test asserts it
stays disabled.

## Limitations

- Streaming is single-process and in-memory. Production needs Kafka between
  collection and processing so events survive a restart and consumers scale out.
- Search is a linear scan with no index, no joins and no subsearches.
- Behavioral baselining runs in batch mode only; it needs a training window.
- The behavioral baseline assumes a clean training window; an attacker present during
  training becomes part of the baseline.
- Offline GeoIP and threat intel for reproducibility — swap the loaders in
  `enrich.py` for MaxMind and MISP in production.
- Single-node OpenSearch with security disabled: lab only.
